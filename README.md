# 忘れ物リマインドボット (ADHDbot)

ADHD特性による行動の困難を補助するボット。仕様書 `carrybotspec.md`（v0.8）に基づく MVP 実装。

- スタック: LINE Messaging API + Google Apps Script + Google Sheets
- スコープ: 仕様書 §2「MVPスコープ」の機能一式（自宅離脱検知＝層A）に加え、Phase 2 の動的アンカー（層B / 任意地点の滞在→離脱検知）まで

## データストア

GASプロジェクトにバインドするスプレッドシートは、指定のGoogle Driveフォルダにあらかじめ作成済みです。

- スプレッドシート: [忘れ物リマインドボット データ](https://docs.google.com/spreadsheets/d/1nd0mYFWPxciYnwDzW4_e-1n5H_OZMUpPQChvXC1sd0Q/edit)
- 格納フォルダ: https://drive.google.com/drive/u/0/folders/1yAMDeVndjywwO4IIzJTtgQwo3p5QJ9X-

シート自体（タブ・ヘッダー）はまだ空です。後述の `setupSpreadsheet()` を一度実行すると、`carry_items` / `routine_items` / `standing_items` / `event_items` / `departure_log` / `dwell_log` / `log` の7シートとヘッダーが自動生成されます。

なお `setupSpreadsheet()` は不足しているシートだけを追加するため、既に一度実行済みの環境で `dwell_log` を足したい場合も、もう一度実行するだけで済みます。

## セットアップ手順

### 1. clasp でプロジェクトを作成しコードをpush

```bash
npm install -g @google/clasp
clasp login

# 既存の上記スプレッドシートにバインドしたスクリプトを新規作成する場合は
# スプレッドシート側のメニュー「拡張機能 > Apps Script」で一度スクリプトを開き、
# そのスクリプトID(URLの /d/<ID>/edit から取得)を .clasp.json に設定する。
cp .clasp.json.example .clasp.json
# .clasp.json の scriptId を書き換える

clasp push
```

### 2. スクリプトプロパティを設定

GASエディタの「プロジェクトの設定 > スクリプト プロパティ」で以下を設定する。

| キー | 値 | 用途 |
|---|---|---|
| `LINE_TOKEN` | LINEチャネルアクセストークン | push/reply送信 |
| `LINE_USER_ID` | push先のLINEユーザーID | push送信先 |
| `WEBHOOK_SECRET` | 任意のランダム文字列 | 自宅離脱通知の共有シークレット検証 (§5.4) |
| `RICH_MENU_IMAGE_FILE_ID` | 背景画像のDriveファイルID | リッチメニュー（任意 / 手順8） |
| `HOME_LAT` | 自宅の緯度 | Open-Meteo天気判定 |
| `HOME_LNG` | 自宅の経度 | Open-Meteo天気判定 |

### 3. 初回セットアップ関数を実行

GASエディタで以下を順に手動実行する（実行権限の承認ダイアログが出る）。

1. `setupSpreadsheet` — シート・ヘッダーの作成、`event_items` 初期セット投入
2. `installTriggers` — 朝push・予防push・前夜push・週次棚卸し・みなし回収・日次クリーンアップの各トリガーを作成

### 4. Webアプリとしてデプロイ

「デプロイ > 新しいデプロイ」→ 種類「ウェブアプリ」→ アクセスできるユーザー「全員」でデプロイし、発行されたURLを控える。

このURLは以下の**3つすべて**の受け口になる（`doPost` 内でペイロードの形から自動振り分け）。

| 送信元 | ペイロード | 振り分け先 |
|---|---|---|
| LINE Messaging API のWebhook | `{"events": [...]}` | `handleLineWebhook` |
| OwnTracks（層B） | `{"_type":"location","lat":35.68,"lon":139.76,"tst":...,"acc":12}` + `?secret=...` | `handleLocationPost` |
| 自宅離脱通知（層A） | `{"secret": "..."}` | `handleHomeDeparture` |

### 5. LINE Developers側の設定

- Messaging APIのWebhook URLに上記デプロイURLを設定し、Webhookを有効化
- 応答メッセージ・あいさつメッセージは無効化推奨（ボット独自の応答ロジックのため）

### 6. iOSショートカットの設定（自宅離脱検知＝層A / §5.4, §5.0）

- ジオフェンス方式: 「自宅から出発」のオートメーションを作成し、半径200〜500mで設定。「実行前に尋ねる」はオフ。アクションは「URLの内容を取得」で上記WebアプリURLへPOST、本文は `{"secret": "<WEBHOOK_SECRETの値>"}`
- Wi-Fi切断方式（フォールバック）: 自宅Wi-FiのSSID切断をトリガーに同様のPOSTを送るオートメーションを併設する
- 両方式とも同一のdoPostを叩くだけなので追加実装は不要（仕様書§5.0）

### 7. OwnTracks の設定（動的アンカー＝層B / §7）

長時間滞在した場所（カフェ・店・職場）から離れたときにリマインドを出すための設定。位置ロガーには **OwnTracks** を使う。

**接続設定**

| 項目 | 値 |
|---|---|
| モード | HTTP（MQTTではない） |
| URL | `<WebアプリのURL>?secret=<WEBHOOK_SECRETの値>` |
| 報告間隔 | 300秒（5分） |
| 測位モード | 静止中も定期的に報告するモード（"Move" 相当）|

**シークレットをURLのクエリ文字列で渡す理由**: OwnTracksは本文に任意のフィールドを足せず、GASの `doPost` はリクエストヘッダーを読めないため、ヘッダー認証もできない。クエリ文字列が唯一の経路になる。

**測位モードの注意**: 「大幅な移動のみ検知」するモードでは静止中に位置を送らないため、滞在（30分間とどまる）が原理的に成立しない。静止中も5分おきに報告するモードにする必要がある。バッテリー消費は増えるので、実際の減り方を見て報告間隔を調整する。

**OwnTracks固有の扱い（実装済み）**

- 座標フィールドは `lng` ではなく `lon`。両方を受けられるようにしてある
- 測位時刻は端末が付ける `tst`(Unix秒) を使う。圏外の間キューに溜めて後からまとめて送信されるため、サーバー到着時刻を使うと滞在時間が潰れて判定できない
- 遅れて届いた点で順序が乱れても、バッファを時刻順に整列してから判定する
- 精度が悪い点（`acc` > 100m）は捨てる。滞在半径150mの判定が壊れるため
- `_type` が `location` 以外（`lwt` / `transition` / `waypoint` 等）の通知は黙って無視する
- OwnTracksはレスポンスにJSON配列を期待するため、常に `[]` を返す

**要確認**: 仕様書§10でも「位置ロガーアプリの現行仕様」は未確認事項として残っている。上記はOwnTracksのHTTPモードの一般的な仕様に基づく実装なので、**最初に手動でPOSTを1回投げて `log` シートに記録が残ることを確認してから**運用を始めること。GASのWebアプリURLはリダイレクトを挟むため、OwnTracks側がリダイレクトを追えているかも併せて確認する。

動作確認は `node test/dwell_test.js` で行える（実機に依存せず、閾値変更の影響を確認できる）。

### 8. リッチメニューの設定（常設ボタン / 任意）

画面下部に[チェック][履歴]の常設ボタンを置く。押すとそのテキストを送信するだけなので、追加のロジックは無い。

1. **背景画像を用意する** — `2500x843` の PNG または JPEG。ボタンの区切りと文字（チェック / 履歴）を描いた画像。LINEが受け付けるサイズは `2500x1686` と `2500x843` のみ
2. その画像を Google Drive に置き、ファイルID（URLの `/d/<ID>/view` の部分）を ScriptProperties の `RICH_MENU_IMAGE_FILE_ID` に設定する
3. GASエディタから `setupRichMenu()` を手動実行する（`DriveApp` を使うため、初回は追加の権限承認が出る）

ボタンの数や文言を変えるときは `CONFIG.RICH_MENU.BUTTONS` を編集し、画像を差し替えて `setupRichMenu()` を再実行する。領域は横一列に等幅で自動計算される。

**注意**: `setupRichMenu()` は既存のリッチメニューを**全て削除してから**作り直す。再実行で古いメニューが溜まらないようにするため。LINE Official Account Manager の画面から手で作ったメニューがある場合も消える。

画像を用意せずに済ませたい場合は、LINE Official Account Manager の画面からリッチメニューを作り、各ボタンのアクションを「テキストを送信」にして `チェック` / `履歴` を設定してもよい（この場合コード側の作業は不要）。

## LINEで使えるコマンド

| 入力 | 動作 |
|---|---|
| 任意のテキスト | 手動登録。「明日 本」「金曜 診察券」「来週 書類」の相対日付プレフィックスに対応 (§5.3a) |
| `チェック` / `出る` | 常備品全件 + 当日のルーチン + 持出中 + 先の予約を返す。あわせて[取消 ○○]ボタンが付き、誤登録をその場で消せる (§5.1b) |
| `なくした 傘` / `忘れた 傘` | 持出中の品を未回収に落とす (§5.2a) |
| `見つかった 傘` | 未回収を回収済に戻す |
| `履歴` | 直近3日の滞在地点を時刻つきで返す (§5.8) |
| `どこ 傘` | その品の未回収日と、その日の滞在地点を返す (§5.7 の中核機能) |

## 主要な設計判断（仕様書との対応）

- **リッチメニューはテキストを送るだけ** (§3 責務分担): 常設ボタンは押すと `チェック` / `履歴` というテキストを送信する。専用のpostbackを用意せず既存のテキスト分岐をそのまま使うので、ボタンからでも手打ちでも経路が1本に保たれる。
- **push型・沈黙優先** (§1 設計原則): 対象0件の日は一切pushしない。全ての判定箇所で `no_items` / `suppressed` を `log` に記録する。
- **「持った」は記録ではなく宣言** (§5.1): このボタンは「今日はこれを持って出る＝外出先でも見ておいてほしい」の意思表示にあたる。押すと持出中になり、予防push(15:00)と滞在地点からの離脱リマインド(層B)の対象になる。押さなければ持出中は空のままで、両方とも沈黙する。つまり**リマインドが要る日だけ押す**という運用になる。この対応関係は押してみないと分からないため、最初の5回だけ案内文を添え、以降は出さない（毎朝同じ説明を付けると文面が伸び、単語だけを読ませる設計が崩れるため）。
- **誤登録は取り消せる**: 経路は2つ。(1) 手動登録の返信にその場で[取り消し]ボタンを添える（打ち間違いは直後に気づくことが多いため）。(2)「チェック」の返信に[取消 ○○]ボタンを並べる。誤登録は一覧を見て気づくものなので、確認と取り消しを別コマンドに分けない。対象は今日以降の予約と持出中のみで、回収済（履歴）と未回収（「見つかった」で戻す）は含めない。状態を変えずに行ごと物理削除するのは、誤登録を履歴に残すと昇格ロジック (§4.3b) の登録回数に混ざるため。
- **予約は「チェック」で確認できる** (§5.1b): 「金曜 診察券」と登録してから予定日の朝までの間、登録できたかを確認する手段が他にないため、オンデマンド確認に予約一覧を含める。相対日付の記法 (§5.3a) が7日先までしか表現できないので、表示日数の上限は設けず全件出す。
- **常備品は通常pushに出さない** (§4.3): `standing_items` は `buildOnDemandCheckText_()` と `weeklyInventoryTrigger()` からのみ参照する。
- **回収確認は行わない・24:00みなし回収** (§5.2a): `midnightSweepTrigger` が持出中を回収済に一括遷移。「なくした/忘れた」申告のみユーザー起点で未回収に落とす。
- **出発時刻の段階的推定** (§5.1a, §7.5): `morningTriggerChecker` を10分おきに実行し、`getMorningPushTimeForToday()` が算出した時刻に達したら1回だけ朝pushを実行する固定時刻トリガーではなくポーリング方式を採用（GASの時刻トリガーは分単位の動的変更ができないため）。
- **push上限と優先度** (§5.5): `PushController.sendPush()` が唯一の送信経路。1日3通の上限に対し、優先度1（自宅離脱の最終push）のみ上限を超えても送信する。
- **動的アンカー（層B / §7）**: 端末は位置をPOSTするだけで、状態機械（`MOVING` ⇄ `DWELLING`）はGAS側に置く。アンカーは滞在中の点の**重心**（屋内のGPSドリフト対策）。滞在半径150mより離脱半径300mを大きく取り、境界での往復による発火の暴れを防ぐ（ヒステリシス）。`LockService` と5分のディバウンスで二重発火を防止する。
- **移動経路は保存しない** (§7 プライバシー方針): 保存するのは滞在地点（`dwell_log` / 1日3〜8行）と離脱時刻（`departure_log` / 座標なし）のみ。状態機械の作業バッファ（ScriptProperties・直近90分）は離脱時に破棄する。両ログとも90日で日次トリガーが物理削除する。
- **同じ日の2回目以降の外出** (§5.4): 1回目（朝）は朝pushの取りこぼしを拾う最終通告として「今朝の候補」を読み上げる。2回目以降（夕方に一度帰宅してから普段持たない鞄で出る等）は今朝の候補が無関係になるため、代わりに**持出中**を読み上げる（15:00の予防pushと同じ考え方）。持出中は自分で登録したときにしか入らないので、何も登録していない日は何回出入りしても沈黙する。`departure_log` に記録するのは1回目だけ — 出発時刻推定は朝の分布を見るものであり、夕方の外出を混ぜると分布が二峰性になるため (§7.5.2)。
- **予防push(15:00)は層Bのフォールバック** (§5.2, §5.9): 15:00固定は「職場・学校からの離脱」を時刻で代用したもので、仕様書は「Phase 2で離脱検知に置換」としている。ただし位置検知は静かに失敗する（端末再起動・権限失効・機内モード・ロガー停止）ため削除せず、**層Bが当日離脱を検知していればスキップ、検知が来ていなければ鳴らす**という排他にした（§1 が定める「離脱検知が来た日は固定時刻をスキップ」の適用）。判定はpushの有無ではなく「離脱を検知できたか」で行う — 検知が動いていれば代役は要らないため。
- **層Aと層Bの二重発火防止**: 自宅は固定ジオフェンス（層A）が担当するため、`HOME_LAT`/`HOME_LNG` から300m以内のアンカーでは層Bのpushを抑止する。
- **LLM不使用** (§6): 天気閾値判定・曜日表引き・キーワード表引き・正規表現前方一致の相対日付解析・中央値/MADのみで構成。外部API呼び出しはOpen-MeteoとCalendarAppのみ。

## 未実装（意図的にスコープ外）

- **滞在地点のラベル付け** (§4.5a): 現状 `dwell_log` の `ラベル` 列は空のまま。手入力すれば `履歴` / `どこ` の表示に反映される。「同一地点に3回滞在 → 名前を付ける?」の自動提案は未実装
- **職場離脱の条件分岐** (§5.4): 「その場所で登録された物」の判定には地点ラベルが必要なため、現状は全ての非自宅アンカーで「持出中があれば鳴らす」。24:00のみなし回収により持出中は毎日リセットされるので、実質「何かを持ち出した日だけ鳴る」挙動になる
- **1週間より先の単発品** (§5.3a / §10): LINEの相対日付は 明日/明後日/来週/曜日名 のみで**最大7日先**まで。カレンダー連携は `event_items` の表引きなので、繰り返し発生する予定（歯科→診察券）は拾えるが、1回きりの予定（3週間後に本を返す）は拾えない（カレンダーのタイトルに品名を書いても読まない / §4.3a）。現状この範囲は `carry_items` シートを直接編集するしかない。
  - **保留の判断**: 実際にどれくらい発生するか分からないため、当面は作らない。カレンダーに `[持ち物:返却本]` のような規約を設けてタイトルから品名を読む案があるが、規約を覚える負担と釣り合うか不明
  - **見直す合図**: 遠い先の予定のためにスプレッドシートを直接開く場面が繰り返し起きたら実装する
- **地図表示（LIFF / §5.8）**: まずテキスト表示で運用し、「地図がないと分からない」場面が実際に起きるか確認してから判断する（仕様書の段階方針どおり）
- 傘以外の天気判定
- 状態機械（着手支援 / Phase 3）
- 販売関連（Wrapper.gsパターン等 / Phase 4）

### 文面切り替えの距離閾値について（§10 の未決事項への回答）

仕様書§10に「文面切り替えの距離閾値300m（離脱判定半径と同値でよいか）」という保留があったが、**同値にはできない**。離脱の発火条件が「アンカーから300m超」であるため、発火時点の距離は必ず300mを超えており、「〜300m → 単語のみ」の分岐が到達不能になる。

そのため文面の閾値を離脱半径より大きい500mに分離した。

| 発火時の実測距離 | 文面 | 意図 |
|---|---|---|
| 300〜500m | `傘` | 境界を跨いだ直後。取りに戻れる |
| 500m〜 | `傘、置いてきた？` | 報告が遅れて既に遠い。行動を要求せず記録だけ促す |

これらは実データが溜まるまでの仮値。仕様書§8「検証指標」に沿って `log` を確認しながらチューニングすること。
