## 1. 目的と背景

ADHD特性による行動の困難を補助するボット。最終的には以下を扱うが、MVPでは忘れ物リマインドに限定する。

### 中核価値：移動検知

**本製品の価値の中心は移動検知にある。** 忘れ物は「思い出す機会」が発生しないことによって起きる。時刻トリガーは本人の生活パターンと合致していることが前提だが、移動検知は本人の意識と無関係に、**忘れ物が確定するその瞬間**を捉える。原理的にこちらが強い。

したがって移動検知はMVPに含める。ただし丸ごとではなく2層に割る。

| | 検知手段 | 必要なもの | カバーする忘れ物 | フェーズ |
|---|---|---|---|---|
| **A: 自宅離脱** | 固定ジオフェンス or Wi-Fi切断 | `doPost` のみ | 持ち出し忘れ | **MVP** |
| **B: 任意地点の離脱** | 動的アンカー（滞在→離脱） | ロガーアプリ・閾値調整・実行時間監視 | 置き忘れ（カフェ等） | Phase 2 |

リスクの大半は移動検知そのものではなく**動的アンカー方式**に由来する。Aが安いのは、自宅が**1地点で、事前に分かっていて、滞在判定が不要**だから。夜は必ず自宅にいるため、滞在を推定する状態機械そのものが要らず、閾値のチューニングも発生しない。動的アンカーの「事前登録不要」という利点はカフェを拾うためのものであり、自宅だけなら不要。

### 時刻トリガーの位置づけ（v0.5で修正）

v0.4では「時刻トリガーは捨てる前提の実装」としたが、**これは撤回する**。ジオフェンスは失敗する（端末再起動、権限失効、機内モード）。時刻トリガーは**フォールバックとして恒久的に残す**。

捨てるのは主役の座であって、実装そのものではない。

```
離脱検知が当日まだ来ていない → 固定時刻に鳴らす
離脱検知が来た              → 固定時刻はスキップ
```

これで二重発火も防げる。

| 困りごと | 対応方針 | フェーズ |
|---|---|---|
| 忘れ物・持ち出したまま忘れる | 持ち物台帳 + 文脈トリガーpush | MVP |
| 着手できない・先延ばし | 次の1手だけ提示し全体像は隠す | Phase 3 |
| 時間感覚が飛ぶ | 実行中の経過時間push | Phase 3 |
| 中断すると戻れない | 状態スナップショット / 復帰時再提示 | Phase 3 |
| タスクが大きすぎて固まる | LLMによる一手分解 | Phase 3 |

### 設計原則

1. **push型であること** — 人がアプリを開く必要がある設計は機能しない。開く動作自体が実行機能を要求するため。
2. **判断コストを乗せない** — 平常時の返信はボタンのみで完結させる。自由入力を要求した時点で使われなくなる。
3. **持ち物がゼロの日は沈黙する** — 毎回鳴るpushは1週間で無視される。発火条件を厳しく保つ。
4. **文面は質問形にしない** — 「傘は持ちましたか？」ではなく「15時から雨。傘。」。事実を投げるだけにして、読んだ瞬間に行動へ変換されるようにする。
5. **平常と違うものだけを出す** — 常備品（財布・鍵・スマホ）は既に習慣化しており情報量がゼロ。毎朝リストに含めると、今日だけのイレギュラーがその中に埋もれて見落とされる。差分だけを出せばリストは通常0〜2個に収まり、鳴ったときの意味が保たれる。

## 2. MVPスコープ

### 含めるもの

- `carry_items` 台帳（持ち物の状態管理）
- **自宅離脱検知（層A）** — `doPost` 受け口 + 離脱時の最終push
- **`departure_log` への離脱時刻記録**
- **出発時刻の段階的推定**（既定時刻 → 全曜日推定 → 曜日別推定 / §5.1a）
- **曜日別の既定時刻設定**（推定前およびフォールバック用）
- `routine_items`（曜日ルーチン）による当日の差分提示
- `event_items` によるカレンダー連携（予定→持ち物の表引き）
- `standing_items`（常備品マスタ）— pushには出さず、オンデマンド/週次でのみ使用
- 朝の天気判定 → 傘の提案 → 「持った」で持出中に登録
- 手動での持ち物登録 + 「明日」プレフィックス
- オンデマンド確認（「チェック」送信で常備品+当日分を全件返す）
- push上限と優先度制御（§5.5）
- 週次棚卸しpush（**実験扱い** / 打ち切り基準あり）
- 前夜push（**実験扱い**）
- 帰宅想定時刻の固定push → 「回収」で台帳を閉じる
- 未回収アイテムの翌朝への繰り越し
- 昇格ロジック（手動登録3回で `routine_items` 化を提案）
- 全イベントの `log` 記録（後の分析用）

### 含めないもの（意図的に除外）

| 除外項目 | 理由 |
|---|---|
| **動的アンカー（層B / カフェ等の置き忘れ）** | ロガーアプリ導入・閾値実測・実行時間監視が必要。複雑性がここに集中する。自宅離脱が安定してから足す |
| 傘以外の天気判定（上着・日焼け止め） | 閾値が増えると外れたときの切り分けが不能になる |
| 状態機械（着手支援） | 台帳が定着してから |
| 販売 | 閾値がハル個人に最適化されており他人の環境で外れる |

**MVPが失うもの**: カフェでの置き忘れは Phase 2 送りとなる。傘の紛失で最も多いパターンであり惜しいが、動的アンカーの複雑性が全てここに集中しているため、自宅離脱の安定を優先する。

MVPを忘れ物に絞る理由は、**成否が客観的に確定する**ため。傘を持ったか否かは事実として残り、閾値チューニングと効果測定ができる。着手支援系は効果が主観にしかならず、パラメータを詰める手がかりがない。

       │              │
       ▼              ▼
┌──────────────┐  ┌────────────────┐

### 責務分担

- **GAS**: 意味的な発火判定（鳴らすべきか）、台帳操作、文面生成
- **Sheets**: 永続化。1シート1責務
- **LINE**: 入出力チャネルのみ。ロジックを持たせない
- **ScriptProperties**: 高頻度の状態フラグ（当日発火済みか等）。Sheetsより高速

## 4. データモデル

### 4.0 3テーブルの役割分担

持ち物は性質の異なる3種類に分ける。**混ぜると判定が濁る**ため、テーブルを分離する。

| シート | 内容 | 通常pushに出るか |
|---|---|---|
| `standing_items` | 財布・鍵・スマホ（常備品） | **出ない**（オンデマンド / 週次のみ） |
| `routine_items` | ゴミ袋(火金)・ジム用品(水) | 出る |
| `carry_items` | 持出中の実体 | 出る |

`standing_items` と `routine_items` は役割が逆（前者=毎日同じで出さない、後者=曜日で変わるので出す）。

### 4.1 `carry_items` シート

| 列 | 型 | 説明 |
|---|---|---|
| id | string | UUID |
| item | string | 持ち物名（例: 傘） |
| 予定日 | date | この日の朝pushに載せる。空欄なら当日扱い |
| 持出日 | date | 持出中になった日 |
| 状態 | enum | `予約` / `持出中` / `回収済` / `未回収` |
| 発生元 | enum | `weather_trigger` / `routine` / `calendar` / `manual` |
| 更新日時 | datetime | 最終更新 |

**状態遷移**

```
(相対日付付きで登録) ──→ 予約 ──(予定日の朝)──→ 朝pushに掲載
                                                    │
(当日登録) ──────────────────────────────→ 持出中 ──(24:00 みなし)──→ 回収済
                                              │
                                              └──(「なくした/忘れた」申告)──→ 未回収
                                                        │
                                                  (翌朝再提示)
```

`予約` はpushに出ない待機状態。予定日の朝トリガーで拾われて初めて表に出る。

**予定日超過の掃除**: 予定日が過ぎても持ち出されなかった `予約` は、`未回収` と同じ扱いで2〜3日後に自動的に落とす（§10 未決）。金曜に登録した診察券が翌週も翌々週も朝pushに出続けるのを防ぐ。

傘専用にせず「持ち出したまま忘れるもの全般」を一つの台帳で扱う。図書館の本、弁当箱、充電器、上着まで同じ仕組みに乗る。

### 4.2 `routine_items` シート（曜日ルーチン）

| 列 | 型 | 説明 |
|---|---|---|
| item | string | 持ち物名 |
| 曜日 | string | カンマ区切り（例: `火,金`）。隔週は `隔週土` 等の拡張記法を検討 |
| 有効 | boolean | 一時的に止められるようにする |

差分の大部分は曜日で決まるため、ここを自動化すると手動登録の負担が減る。毎日中身が変わるので、常備品リストと違って読む価値が維持される。

### 4.3 `standing_items` シート（常備品マスタ）

| 列 | 型 | 説明 |
|---|---|---|
| item | string | 持ち物名（財布・鍵・スマホ等） |
| 有効 | boolean | |

**通常の朝pushには絶対に含めない。** 用途はオンデマンド確認と週次棚卸しの2つのみ。

### 4.3a `event_items` シート（予定→持ち物マッピング）

イレギュラー品は一括では扱えない。検知手段ごとに4分類する。

| 種類 | 例 | 検知手段 |
|---|---|---|
| 天候由来 | 傘、日焼け止め | Open-Meteo（§5.1） |
| 予定由来 | 診察券、ジム用品、名刺 | **カレンダー連携（本節）** |
| 周期由来 | ゴミ袋、資源ごみ | `routine_items` |
| 純粋な単発 | 返却する本、借りたもの | **検知不可能**（§5.3aで代替） |

| 列 | 型 | 説明 |
|---|---|---|
| keyword | string | カレンダー予定タイトルに含まれる語（例: 歯科） |
| items | string | カンマ区切りの持ち物（例: 診察券,保険証） |
| 有効 | boolean | |

**表引きから始めること。LLM推論は使わない。** カレンダーのタイトルは「13:00 田中さん」のように情報が薄いことが多く、LLMに投げても推論が外れる。外れた提案を毎朝出すのは原則3（沈黙）に真っ向から反する。

**表引きで拾えなかった予定は黙って無視する。**「予定がありますが持ち物は分かりません」を出す価値はない。

### 4.3b 昇格ロジック（`routine_items` への学習）

同じ物が手動登録され続けたら、それはもうイレギュラーではない。

```
「図書館の本」が隔週土曜に3回登録される
  → 「毎週これ出す?」+ ボタン[はい / いいえ]
  → はい → routine_items へ昇格
```

**初期設定をほぼゼロにできる**のがこの仕組みの価値。§9で設定の摩擦が販売時の最大の脱落要因と整理しているが、使いながら設定が育つ構造にすればこの問題がかなり緩む。

### 4.4 `log` シート

| 列 | 型 | 説明 |
|---|---|---|
| timestamp | datetime | |
| event | string | `weather_check` / `push_sent` / `postback` / `no_items` / `suppressed` |
| detail | json | イベント固有データ（降水確率、対象item等） |

閾値チューニングと効果測定に使う。**MVPの価値はここに集まる**ので最初から入れる。

### 4.5a `dwell_log` シート（滞在地点 / Phase 2）

Phase 2 の状態機械が計算する滞在アンカーを、破棄せず記録する。**追加の検知機構は不要**（既に計算済みのものを残すだけ）。

| 列 | 型 | 説明 |
|---|---|---|
| 日付 | date | |
| 到着 | time | 滞在開始 |
| 出発 | time | 離脱時刻 |
| lat / lng | number | アンカー（滞在中の点の重心） |
| ラベル | string | 手動 or 提案により設定。未設定可 |

1日あたり3〜8行。全経路を残す場合（数百〜数千行）と比べて桁が2つ小さい。

#### ラベル付け

**ラベルがなければ `dwell_log` は座標の墓場になる。** テキスト表示では座標を並べても判別できないため、ラベル付けは実質的な前提機能。

```
同一地点に3回滞在 → 「ここに名前を付ける?」
  → 以降その地点は名前で表示される
```

§4.3b の昇格ロジックと同じ構造（使うほど設定が育つ）。ラベルが付くほど地図表示の必要性自体が下がる。

#### 副産物：場所ベースのルーチン

同一地点への反復滞在は行動パターンそのもの。「ジムに行った日は必ずタオルを持ち出している」が観測できれば、**曜日ベースより精度の高いルーチン**を `routine_items` に生成できる。これは経路データからは得られない。

### 4.5 ScriptProperties

| キー | 用途 |
|---|---|
| `LINE_TOKEN` | チャネルアクセストークン |
| `LINE_USER_ID` | push先 |
| `fired_date_morning` | 当日の朝push済みフラグ |
| `fired_date_evening` | 当日の夕方push済みフラグ |

## 5. トリガー仕様

### 5.0 確定値（v0.8）

| 項目 | 値 | 備考 |
|---|---|---|
| 出発既定時刻 | 平日 7:00 / 休日 9:00 | 段階0のフォールバック値（§5.1a） |
| **朝push** | **平日 6:40 / 休日 8:40** | 出発の20分前 |
| **予防push** | **平日 15:00** | 学校の終業時刻。Phase 2で離脱検知に置換 |
| 回収確認push | **廃止** | 24:00にみなし回収（§5.2a） |
| 週次棚卸し | 月曜の夜 | 実験扱い |
| 自宅離脱の検知 | ジオフェンス（iOSショートカット） | Wi-Fi切断をフォールバックとして併設 |
| 端末 | iPhone | |
| `event_items` 初期セット | 打ち合わせ / 面談 → 名刺, PC | |

**ジオフェンスを選択したが、Wi-Fi切断を代替から外さずフォールバックとして残すこと。** ショートカットのオートメーションは端末再起動後に発火しなくなる場合があり、失敗が静かに起きる。実装は同じ `doPost` を叩くだけで追加コストがほぼない。


### 5.1 朝トリガー（出発想定時刻の15〜20分前）
```
1. 未回収アイテムがあれば先に提示
2. carry_items から 予定日=今日 かつ 状態=予約 を取得
3. routine_items から当日の曜日に該当する行を取得
4. CalendarApp で当日の予定を取得し、event_items で表引き
   （ヒットしない予定は無視）
5. Open-Meteo で当日 6:00〜22:00 の予報取得
   傘判定:
   - 降水確率の最大値 >= 50%   ← 要チューニング
   - かつ 降水量 >= 0.5mm/h の時間帯が1つ以上存在
6. 2〜5 を合流させて1通にまとめる（重複は名寄せ）
7. 0件 → 沈黙
8. push「傘・ゴミ袋・診察券」+ ボタン[持った]
9. 「持った」→ carry_items を持出中に更新
```

**push時刻の決定は §5.1a を参照。** 既定時刻から始まり、`departure_log` の蓄積に応じて自動的に推定値へ移行する。

**降水確率のみで判定しない**こと。20%が終日続く日に毎回引っかかる。降水量とのANDを取る。

文面は単語のみ。出発直前・移動中に読むため、質問形にすると視認と行動変換が遅くなる。

### 5.1a 出発時刻の段階的推定

**既定時刻から始まり、使うほど自動で寄っていく。** 段階の移行は自動で、ユーザー操作を要しない。

```
段階0（初日〜）    曜日別の既定時刻（手動設定）
   ↓ 全体 n>=10 かつ MAD<40分
段階1（2週間〜）   全曜日まとめた分布から推定
   ↓ 該当曜日 n>=8 かつ その曜日のMAD<40分
段階2（2ヶ月〜）   曜日別の分布から推定
```

#### 曜日ごとに独立して昇格させる

「月曜と火曜は段階2、水曜はサンプル不足で段階1」という**混在状態が通常**である。曜日ごとに独立判定すれば待ち時間が最短になる。

#### 降格

引っ越し・転職で分布が変わると、ローリングウィンドウから古いデータが抜ける過程でMADが一時的に跳ね上がる。**閾値を割ったら段階0（既定時刻）に戻す。** これは正しい挙動であり、無理に推定を続けるより安全。

#### 既定時刻は曜日別に持つ

段階0のフォールバック値。全曜日一律ではなく曜日別に設定する。平日7:30・土日9:00程度の粗い設定でも、一律より外れが大幅に減る。推定へ移行後も降格時の戻り先として残る。

#### 推定値をユーザーに見せない

「7:42に鳴らします」と表示すると、その時刻に間に合わせようとする意識が働き、§7.5.6 のフィードバックループを本人が強化してしまう。**ボットは黙って寄せる。**

週次の振り返り（「今週の推定: 平日7:40」）程度なら害は小さい。`log` には必ず残す（デバッグおよびMAD閾値のチューニング根拠）。

統計手法の詳細（中央値の使用、25パーセンタイル、ローリングウィンドウ）は §7.5 を参照。

### 5.1b オンデマンド確認（「チェック」送信時）

`standing_items` 全件 + 当日の `routine_items` + `carry_items` の持出中を返す。

押されたときだけ返すので、常備品を全件出して問題ない。不安なときに自分から引ける逃げ道として機能する。手動トリガー（「出る」で持ち物リストを返す）も実装が同一なので同時に用意する。

### 5.1c 週次棚卸し（週の頭 / **実験扱い**）

`standing_items` 全件のみを流す。常備品の存在を忘れないための保険。

**通常pushとは別便にする。** 同じ通に混ぜると常備品が毎日出るのと変わらなくなり、原則5に反する。

> **⚠ 実験ステータス**
> 中身が毎回同じpushは、数回流れた時点で読まれなくなるのがpushの通例。読まれないpushは無害ではなく、他のpushへの注意も削る。
> **打ち切り基準**: `log` に「棚卸しpush後に何らかの操作があったか」を記録し、**4週回して反応ゼロなら削除する**。
> 週1という低頻度なら耐える可能性もあるため、実データで判断する。

### 5.2 予防push（平日 15:00）

**帰宅時刻の推定ではなく、特定の場所を離れる時刻に鳴らす。** 現在は学校の終業時刻が15:00であるため、この値を採る。

構造としては §5.4 の「職場離脱」と同じであり、時刻トリガーで代用している形。**Phase 2 の動的アンカーで自動化される**（学校は毎日長時間滞在するため確実に拾える。授業が延びた日も早退した日も実際の離脱で鳴る）。15:00固定はその暫定版。

```
1. carry_items から 持出中 を全取得
2. 0件 → 何もしない（沈黙）
3. 朝に「持った」の応答がなかった日 → 何もしない
4. push「傘・弁当箱」
```

条件3が重要。持ち出したか不明な状態で聞くと外れが続き、push全体の信頼が失われる。

**文面は単語のみ。「戻った？」ではない。** この時点では回収も未回収も確定していない。その場を離れる前に手元を確認させるのが目的であり、まだ取りに戻れる。

**このpushは台帳を閉じない**（状態遷移を起こさない）。回収の確定については §5.2a を参照。

### 5.2a 回収確認は行わない（v0.8で決定）

`carry_items` の `持出中 → 回収済` の遷移だけはボットに観測できない。傘を持ち帰ったかを知る手段がないため、当初は夕方に「戻った？」と尋ねる設計だった。**これを廃止する。**

#### 廃止の理由

回収確認そのものにユーザー価値がない。傘を持ち帰った人にとって「戻った？」は既知の情報であり、ボタンを押す動作は純粋なコストである。**ボット側の都合で人に入力させる機能**であり、設計原則2（判断コストを乗せない）に反する。押し忘れが常態化する見込みが高く、押し忘れは台帳を汚す。

#### 代替：みなし回収

```
24:00  持出中 → 回収済 に自動遷移
```

傘は大半の日に持ち帰るため、**デフォルトを「回収済」に倒すほうが現実に合っている**。

失くした日だけ本人が申告する。忘れ物に気づいた瞬間は本人が最もよく分かっており、その入力のほうが確実。

```
「なくした 傘」「忘れた 傘」 → 未回収 に落とす
```

Phase 2 では自宅アンカーへの到着で閉じることもできるが、到着時点で持ち帰ったかは判別できないため結局「みなし」になる。時刻によるみなしで十分。

#### 台帳を閉じる必要がある理由（参考）

回収確認pushは廃止するが、状態を閉じること自体は必要である。

1. **翌朝の誤提示を防ぐ** — 持出中のまま残った傘が翌朝もpushに出る。数日続けば朝pushの信頼が落ちる（最大の理由）
2. **「どこ 傘」の逆引きを成立させる**（§5.7）— 未回収の発生日が分からないと `dwell_log` と繋がらない
3. **昇格ロジックの材料**（§4.3b）

### 5.3 手動登録

任意のテキスト送信を持ち物名として `carry_items` に登録。確認は返さず、登録した事実だけ短く返す。

### 5.3a 相対日付指定（純粋な単発への対応）

純粋な単発品（返却する本、借りたもの、予定に紐づく持ち物）は**検知する方法が存在しない**。ボットは本を借りた事実を知りようがない。

したがって問題を読み替える。これは検知の問題ではなく**タイムシフトの問題**である。「これを持っていく」と気づく瞬間は朝ではなく、予定が決まった瞬間や事象が起きた瞬間（本を借りた直後、診察を予約した直後）。そのタイミングで拾えれば当日の朝に出せる。

#### 記法

```
「本」          → 今日
「明日 本」      → 翌朝
「金曜 診察券」  → 次の金曜
「来週 書類」    → 翌週月曜
```

曜日名 + 「明日 / 明後日 / 来週」のみ。**正規表現の前方一致で解析でき、LLMは不要**（§6）。

#### 自由入力の日付解析はしない

「9月15日の朝に診察券」のような文の解析にはLLMが必要になり、§6の前提を崩す。

より重要な理由として、**日付入力はADHD特性と相性が悪い**。入力の瞬間に「何日だっけ」と考える必要が生じ、キャプチャの速さが失われる。手動登録の価値は3秒で放り込めることであり、ここにコストを乗せてはならない。

#### 時刻は指定させない

持ち物は当日の朝pushに載せれば足りる。時刻指定は入力を長くし、朝以外に鳴るpushは §5.5 の上限を圧迫する。

#### カレンダー連携との関係

`event_items`（§4.3a）は初期キーワードセットの用意という設定コストがあるが、本機能は**設定ゼロで思いついた瞬間に登録できる**。カレンダー連携が拾えなかった予定を人が補完する経路として機能し、両方あると穴が塞がりやすい。

どちらがよく使われるかを §8 で計測する。手動が圧倒的なら `event_items` は不要と判断してよい。

### 5.3b 前夜push（**実験扱い**）

翌日の予定を前夜に提示し、持ち物の登録を促す。

発火条件: 翌日にカレンダー予定があり、かつそれが `routine_items` にない**非定常な予定**であること。この条件なら週1〜2回に収まる。予定がない日は沈黙。

> **⚠ 実験ステータス** — 毎晩出すと死ぬ。反応率で残すか決める。

### 5.4 移動検知push（**本製品の中核** / 層A=MVP, 層B=Phase 2）

#### 発火場面

| 離脱元 | 内容 | 優先度 | フェーズ |
|---|---|---|---|
| 自宅 | 持ち出し忘れ（傘・ルーチン・予定由来） | 最高 | **MVP（層A）** |
| カフェ・店 | 置き忘れ（傘・その場で使った物） | 高 | Phase 2（層B） |
| 職場 | 持出中リスト | **条件付き** | Phase 2（層B） |

自宅とカフェで**忘れ物の二大パターン（持ち出し忘れ / 置き忘れ）**をカバーする。傘の紛失はカフェで起きることが多く、動的アンカー方式（§7）で事前登録なしに拾える点がPhase 2で効く。

#### 層A: 自宅離脱の実装（MVP）

滞在判定が不要なため、端末側のジオフェンス通知を `doPost` で受けるだけで成立する。

```
端末（iOSショートカット「出発」/ 自宅Wi-Fi切断）
  → GAS Web App doPost
    → シークレット検証
    → ディバウンス（5分）/ 当日発火済みチェック / LockService
    → 朝pushに応答があったか確認
       応答あり → 沈黙
       応答なし → 最終push
    → departure_log に離脱時刻を記録
```

- GAS Web App はアクセス権「全員」が必要なため、**共有シークレット検証は必須**
- ジオフェンス半径は **200〜500m**。小さいとゴミ出しや郵便受けで誤発火し、大きいと引き返せない距離まで行ってから鳴る
- 境界上で往復すると数秒差で二重に叩かれるため `LockService` 必須
- Wi-Fi切断トリガーは位置情報権限が不要で精度も高い。代替として同等に扱える

**時刻トリガーとの排他**: 離脱検知が当日来ていれば固定時刻のpushはスキップする（§1）。

#### 職場離脱に条件を付ける理由

職場離脱は毎日必ず発火する。中身が同じpushが毎日鳴ると原則5（差分提示）に反して読まれなくなり、夕方pushとも内容が重複する。

発火条件: 持出中の物のうち、**その場所で登録された物、または朝に持ち出した物**がある場合のみ。傘を持って出た日だけ鳴り、持たなかった日は黙る。

#### 距離による文面切り替え

「引き返せる場合のみ鳴らす」では狭すぎる。正しくは、**戻るコストと失う物の価値を比較して判断できる情報を渡す**こと。距離で発火を切るのではなく、文面を変える。

| 距離 | 文面 | 意図 |
|---|---|---|
| 〜300m | `傘` | 取りに戻れる |
| 300m〜 | `傘、置いてきた？` | 記録を促す（行動を要求しない） |

1km離れてから「傘」と言われても戻らないかもしれないが、**「今日どこかに傘を置いてきた」という情報自体に価値がある**。失くしたことに気づくのが3日後になるより圧倒的によい。後者は行動を要求しないため、移動中でもコストにならない。

#### 移動中pushの外れが持つコスト

移動中は最も反応しにくい時間帯（歩行中、乗車中）であり、外れたpushは読まれずに既読だけ付く。「このボットの通知は移動中に鳴る＝どうせ今は対応できない」という学習が起きると、**朝の準備pushまで無視される**。

これは「鳴らすな」ではなく「**外さないための条件を厳しくしろ**」という要求である。中核機能だからこそ精度を守る。

### 5.5 push上限と優先度

各pushはそれぞれローカルな発火条件を持つが、**互いを見ていない**。条件が重なった日に一斉に鳴る。

最悪ケース: 月曜 + 前夜push + 朝pushに無応答 + 離脱push + 夕方push + 週次棚卸し = **5通**。原則3が破れる。

#### ルール

`log` から当日の送信数を数え、上限（3通）で打ち切る。ただし単純な上限では重要なpushが切られるため、優先度を持たせる。

| 優先度 | push | 理由 |
|---|---|---|
| 1（最高） | 移動検知push（§5.4） | 引き返せる最後の機会。他を犠牲にしても通す |
| 2 | 朝の準備push | |
| 3 | 予防push（15:00） | |
| 4 | 前夜push | |
| 5（最低） | 週次棚卸し | 他と重なった週は飛ばしてよい |

週次棚卸しを夜に移すだけでも衝突は減り、朝の枠が空く（§10 未決）。

### 5.7 履歴問い合わせ（Phase 2）

`dwell_log` への問い合わせ。**すべてユーザー起点**のため §5.5 のpush上限の対象外。

#### コマンド記法

相対日付指定（§5.3a）と記法を揃え、覚えることを増やさない。**LLM不要**（§6の前提を維持）。

```
「履歴」          → 直近3日の滞在
「履歴 9/1」      → その日の滞在
「履歴 先週の火曜」 → 相対日付も可
「どこ 傘」        → 傘の未回収日とその日の滞在地点
```

#### 「どこ 傘」が中核

3つの問い方のうち、**物からの逆引きが最も価値が高い**。

| 問い方 | 実装 | 評価 |
|---|---|---|
| 日付指定 | 日付パースのみ | 補助的 |
| **物から逆引き** | `carry_items` の `未回収` 日 → `dwell_log` | **中核**。台帳と滞在ログが繋がって初めて成立する |
| 場所から逆引き | ラベル検索 | ラベル未設定だと実用性が低い |

物からの逆引きは `dwell_log` を持つ理由そのものであり、忘れ物ボットとして筋が通る。台帳だけ・位置ログだけのツールには出せない機能。

### 5.8 滞在地点の表示（Phase 2）

#### 段階を踏む：まずテキスト

```
9/3の滞在
10:20-11:45 (未設定)
12:30-18:10 職場
18:40-19:15 (未設定)
```

**地点名がなくても時刻だけで大半は思い出せる。** 実装はSheetsを読んで整形するだけ（数十行）。これを運用し、「地図がないと分からない」場面が実際に発生するか確認してから地図表示へ進む。テキストで足りるなら地図は不要。

#### 地図表示の3方式

| 方式 | 実装 | 評価 |
|---|---|---|
| LINE Location Message | 最も簡単 | **1メッセージ1地点**。3〜8箇所で同数のメッセージが飛ぶ。体験が悪い |
| 静的地図画像 | 中 | 1枚にまとまり見た目は良いが地図画像APIが必要。Google Static Mapsは従量課金。OSM系代替の無料枠・商用条件は**要確認** |
| **LIFF（Webページ）** | 重い | 表現力が段違い。Leaflet + OSMタイルで表示自体は無料。GASの `HtmlService` で完結しホスティング不要 |

**LIFFを推奨する。** 理由は、地図を見る場面がpushではないため。「昨日どこ寄ったっけ」と自分から尋ねる状況であり、画面を開く手間が許容される（移動中のpushを厳しく制限した §5.4 とは要求が逆）。

また滞在地点は**時刻情報とセットで意味を持つ**。「10:20-11:45にここ」が分かって初めて心当たりが立つ。静的画像はマーカーに時刻を載せづらく、Location Messageは1件ずつしか見られない。LIFFならリストと地図を並置できる。

LIFF上でラベル付けも行えるため、`dwell_log` を育てる導線を兼ねられる。

## 6. 技術要素・外部サービス

### MVPはLLM APIを必要としない

MVPの全機能がルールベースで実装できる。**そのほうが望ましい。** 速く、無料で、同じ入力に同じ出力が返る。忘れ物リマインドは毎朝同じ形式で鳴るものであり、生成の揺らぎは害にしかならない。

| 機能 | 処理 |
|---|---|
| 天気判定 | 閾値比較 |
| 曜日ルーチン | 表引き |
| カレンダー連携 | キーワード表引き（§4.3aでLLM推論を明示的に排除） |
| 手動登録 | 文字列をそのまま格納 |
| 相対日付指定 | 正規表現の前方一致 |
| 履歴問い合わせ | コマンドプレフィックス + 日付パース |
| 出発時刻推定 | 中央値・MAD |
| 移動検知 | 距離計算 |

副次的な効果として、GASの実行時間とAPIコストの双方が問題にならない。外部API呼び出しがOpen-Meteoとカレンダーのみのため、実行時間の日次上限にも余裕がある。販売時も購入者にLLMのAPIキーを設定させる必要がなく、**ランニングコストゼロで頒布できる**（設定の摩擦が一段減る）。

LLMが必要になるのは Phase 3（タスク分解とリフレーミング）から。

**唯一の懸念**は手動登録の表記ゆれ（「傘」「かさ」「折りたたみ」が別アイテムとして溜まると昇格ロジックが発火しない）。ただしLLMを持ち出す前に正規化テーブルで対処できる。自分用では表記を揃えれば済むため、実質的には販売時の課題。

| 要素 | 用途 | 費用 | 備考 |
|---|---|---|---|
| Google Apps Script | 実行環境・トリガー | 無料 | 実行時間の日次上限あり。Phase 2で要監視 |
| Google Sheets | データ永続化 | 無料 | |
| Google Calendar (`CalendarApp`) | 予定由来の持ち物判定 | 無料 | GASから標準アクセス可。追加認証不要 |
| LINE Messaging API | 入出力 | 要確認 | 無料枠の通数上限を確認。自分用なら問題ない見込みだが販売時は必須確認 |
| Open-Meteo | 天気予報 | 無料 | APIキー不要、`UrlFetchApp` から直接叩ける。**無料枠は非商用条件のため販売時は要確認**。代替: 気象庁JSON（非公式エンドポイント、安定性は劣る） |

### MVPで追加（層A）

| 要素 | 用途 | 備考 |
|---|---|---|
| GAS Web App (`doPost`) | 自宅離脱の受け口 | アクセス権「全員」+ 共有シークレット検証が必須 |
| iOSショートカット / MacroDroid | 自宅ジオフェンス | オートメーション「出発」。実行前に尋ねるをオフ。iCloudリンクで雛形配布可 |
| 自宅Wi-Fi切断トリガー | 同上（代替） | 位置情報権限が不要で精度も高い |

### Phase 2 で追加（層B）

| 要素 | 用途 | 備考 |
|---|---|---|
| 位置ロガーアプリ | 位置のPOST | OwnTracks / Overland 等。大幅移動検知モードがあるもの。**現行仕様は要確認** |
| LIFF + Leaflet + OSMタイル | 滞在地点の地図表示 | GASの `HtmlService` で完結。表示自体は無料。OSMタイルの利用ポリシーは**要確認** |

- **Painline**: Wrapper.gs によるライブラリ配布アーキテクチャ（販売時）

## 7. Phase 2: 動的アンカー（層B）

**自宅離脱（層A）はMVPに含まれる**（§1、§5.4）。本章が扱うのは、事前登録なしに任意の滞在地点を検知する層Bのみ。カフェ・店・職場での**置き忘れ**をカバーする。

着手条件は「MVPの自宅離脱が安定して動作していること」。回収率の良否は問わない。

Phase 2 のスコープ:

- 動的アンカーによる任意地点の滞在→離脱検知（カフェ・職場の置き忘れ）
- `dwell_log`（滞在地点の記録 / §4.5a）
- 履歴問い合わせ（§5.7）と滞在地点の表示（§5.8）
- ラベル付け

なお v0.2 でPhase 2の価値が上がった。当初は夕方の回収タイミング精度のためだったが、**朝の出発検知にも同じ「自宅を離脱」イベントがそのまま使える**。出発時刻の日次変動は固定時刻では原理的に扱えないため、朝夕どちらの精度問題も単一の仕組みで解決する。

### ⚠ 朝は検知だけでは足りない（層A・層B共通）

**離脱を検知した時点で朝のリマインドは手遅れ**である。「傘を持たずに出ましたね」は情報として無価値。朝と夕方で必要な仕組みが異なる。

| | 必要なもの | 実現フェーズ |
|---|---|---|
| 朝（持ち出し） | **予測**（離脱の15〜20分前に鳴らす） | Phase 2.5 |
| 夕方（回収） | 検知（離脱時に鳴らせばよい） | MVP（層A）/ Phase 2（層B） |

MVPの自宅離脱pushは「出た後の最終通告」であり、まだ引き返せる距離（200〜500m）に賭けた保険である。朝の完成形は Phase 2.5 の予測を待つ。

**MVP初日から離脱時刻を `departure_log` に残すこと。** MVPを回す期間がそのまま Phase 2.5 の準備期間を兼ねる。

### 前提: LINE単体では実現不可

LINE Messaging API で位置情報が取れるのはユーザーが手動で位置情報メッセージを送ったときのみ。LIFFもフォアグラウンドでしか動かない。バックグラウンドでの移動検知手段が構造的に存在しないため、検知は端末側（OS / ロガーアプリ）に委ねる。

### 滞在→離脱の状態機械

固定ジオフェンス（自宅・職場の事前登録）ではなく、**一定時間居座った場所を動的にアンカー化**する方式を採る。事前登録が不要になり、傘の紛失が起きやすいカフェや店もカバーできる。

```
MOVING ──(直近K点が半径150m以内 かつ 30分以上)──→ DWELLING(anchor)
DWELLING ──(anchorから300m超)──→ 離脱イベント発火 → MOVING
```

| パラメータ | 値 | 根拠 |
|---|---|---|
| 滞在判定半径 | 150m | |
| 離脱判定半径 | 300m | 滞在半径より**大きくする**。同値だとGPS揺れで境界を往復し発火が暴れる（ヒステリシス） |
| 滞在時間閾値 | 30分 | 信号待ち・コンビニ寄りを自動的に除外 |
| ディバウンス | 5分 | |

実装上の注意:

- アンカーは滞在中の点の**重心**を使う。屋内はドリフトが大きく1点固定では100m以上ずれる
- 点が2つで30分空いているケース（報告欠落）を滞在と誤認しないガードが必要
- 二重発火防止に `LockService` 必須

### 責務分担（Phase 2）

- **端末側**: 位置のPOSTのみ。判断ロジックを一切持たせない（持たせると環境ごとに挙動がズレてサポート不能）
- **GAS側**: 滞在判定、離脱判定、発火可否、台帳突き合わせ

### プライバシー方針（v0.7改訂）

**移動経路（軌跡）は保存しない。滞在地点のみを保存する。**

v0.6までは「生の座標を一切蓄積しない」としていたが、失くし物の追跡と行動パターン学習のために滞在地点の保存を解禁する。ただし経路は解禁しない。

| データ | 保存 | 理由 |
|---|---|---|
| 移動中の点（軌跡） | **しない** | 歩行中に物を失くすことはまずない。情報密度が低く、量は滞在地点の100倍規模になる |
| 滞在地点（`dwell_log`） | する | 失くし物は「座った場所・立ち寄った店」で発生する。1日3〜8行に収まる |
| 離脱時刻（`departure_log`） | する | 出発時刻推定の学習データ。座標は含まない |

状態機械の作業バッファ（ScriptProperties、直近90分ぶん）は従来どおり離脱時に破棄する。

#### 保持期間

| データ | 期間 | 根拠 |
|---|---|---|
| `dwell_log` | **90日** | 出発時刻推定は30〜60日で足りるが、失くし物の追跡には短い。長く持つほど追跡範囲は広がりリスクも比例する |
| `departure_log` | 90日 | ローリングウィンドウ（30〜60日）+ 余裕 |

**GASの日次トリガーで期限切れ行を物理削除すること。** 自動削除を実装しなければ、決めた保持期間は意味を持たない。

#### 全経路記録について

技術的には可能だが、**用途が曖昧なまま位置履歴を溜めるのが最も危険**である。「あとで何かに使うかも」で始めた蓄積は使われないまま残り続ける。

実装するとしても Phase 2 のオプション（**デフォルトOFFのオプトイン**）とし、商品説明への明記を必須とする。常時トラッキングでは1日2000点規模になり、GAS実行時間の上限（§6）にも触れる。

## 7.5 出発時刻推定の統計仕様（MVP機能 / §5.1a の詳細）

**本節はMVPの一部である。** v0.5までは「Phase 2.5」として独立フェーズ扱いだったが、層AをMVPに入れた時点で `departure_log` が初日から蓄積されるため、独立させる必然性がなくなった。段階的に有効化されるだけであり、実装も1箇所に収まる。

段階移行のルールは §5.1a を参照。本節は統計手法の詳細のみを扱う。

### 7.5.1 `departure_log` シート

| 列 | 型 | 説明 |
|---|---|---|
| date | date | |
| 曜日 | string | |
| 離脱時刻 | time | 自宅アンカーからの離脱 |
| 予測時刻 | time | その日に予測していた時刻（誤差検証用 / null可） |

座標は保存しない（§7 プライバシー方針）。MVP初日から記録を開始する。

### 7.5.2 統計手法

**中央値を使う。平均は使わない。**
月1回の11時出発が平均を30分ずらす。分布の裾が重いため、ロバストな統計量でなければ使い物にならない。

**曜日でセグメントする。**
平日と休日は別の分布であり、混ぜると二峰性になって中央値が谷に落ちる。ただし曜日ごとに切ると1ヶ月で4サンプルしか溜まらないため、段階的に進める（移行ルールは §5.1a）。

**直近30〜60日のローリングウィンドウ。**
季節性（夏冬の出発時刻のずれ）に自然に追随する。全期間の中央値では追随しない。

### 7.5.3 push時刻の決定

損失が非対称である点を利用する。

| ずれ | 損失 |
|---|---|
| 早すぎる | 軽微（まだ準備中だが、取りに行ける） |
| 遅すぎる | **完全に無価値**（もう出ている） |

したがって中央値ちょうどではなく、早い側に寄せる。

```
push時刻 = percentile(離脱時刻, 25) - 20分
```

### 7.5.4 予測を諦める条件（重要）

**MAD（中央絶対偏差）が閾値を超えたら予測しない。**

| パラメータ | 値 |
|---|---|
| MAD閾値 | 40分（要チューニング） |
| 最小サンプル数 | 10 |

いずれかを満たさない場合は推定を無効化し、曜日別の既定時刻へ**降格**する（§5.1a）。**外れた予測で鳴らすのは、鳴らさないより悪い。**

判定は曜日ごとに独立して行う。全体分布と曜日別分布のそれぞれで評価する。

### 7.5.5 二段構え

予測と検知を組み合わせることで、予測精度が低い期間も安全に運用できる。

```
予測時刻 ─→ 準備push「傘・ゴミ袋」
              │
              ├─(ボタン応答あり)─→ 離脱時は沈黙
              │
              └─(応答なし)
                    │
              実際の離脱を検知 ─→ 最終push「傘」
```

準備pushに反応があれば離脱時は黙る。反応がなければ出た瞬間に最終pushを入れる。離脱判定半径は300mなので、まだ引き返せる距離に収まる。

この構成により**推定は後から有効化できる**。MVPでは既定時刻の準備push + 自宅離脱の最終push（層A）で動き出し、`departure_log` が溜まるにつれて準備pushの時刻だけが自動的に寄っていく。実装の追加は不要。

### 7.5.6 注意点

**フィードバックループ**
予測時刻のpushが実際の出発を早める可能性がある。自分の出力を学習データにすることになり、厳密には汚染。実用上は無視できる程度と考えられるが、精度が不自然に上がる・収束が速すぎる場合はこれを疑う。

**予測誤差のログ**
`departure_log` の `予測時刻` 列に当日の予測値を残し、実測との差を追跡する。MAD閾値のチューニング根拠になる。

## 8. 検証指標（MVP後1週間で確認）

| 指標 | 意味 | 判断 |
|---|---|---|
| 朝pushの空振り回数 | 降水確率50%閾値の妥当性 | 空振り多 → 閾値引き上げ |
| 夕方pushの回収率 | 固定時刻の妥当性 | 低い → Phase 2（位置情報）へ進む根拠 |
| **自宅離脱検知の稼働率** | 層Aが実際に発火しているか | 低い → ジオフェンス半径 or Wi-Fiトリガーへの切替を検討。**時刻トリガーのフォールバックが機能しているかも併せて確認** |
| **離脱pushから帰宅までの回収率** | 「まだ引き返せる」仮説の検証 | 低い → 半径200〜500mの見直し |
| 手動登録の使用回数 | 台帳という発想自体の有効性 | **ゼロなら設計を根本から見直す** |
| 朝pushの平均item数 | 差分提示が機能しているか | 常時3個超 → `routine_items` に常備品が混入している疑い |
| 棚卸しpush後の操作有無 | 週次棚卸しの有効性 | **4週で反応ゼロなら機能削除**（§5.1b） |
| オンデマンド確認の使用回数 | 常備品を出さない判断の妥当性 | 頻繁 → 差分だけでは不安が残っている。設計再考 |
| 手動登録 vs カレンダー連携の発生比 | `event_items` の要否 | 手動が圧倒的 → `event_items` は不要と判断してよい（§5.3a） |
| 推定段階の到達状況 | 曜日別推定まで届くか | 段階0に留まる曜日が多い → 出発時刻が不規則。既定時刻の運用を継続 |
| **テキスト表示で足りた割合** | 地図表示（LIFF）の要否 | 足りている → LIFF実装を見送ってよい（§5.8） |
| 「どこ 傘」の使用回数 | `dwell_log` を持つ価値の検証 | ゼロなら滞在地点の保存自体を再考 |
| ラベル設定率 | `dwell_log` が座標の墓場になっていないか | 低い → 提案の導線を見直す |

## 9. ロードマップ

```
Phase 1 (MVP)  台帳 + 天気/カレンダー判定 + 相対日付指定
               + 自宅離脱検知（層A）★中核
               + 出発時刻の段階的推定（既定→全曜日→曜日別 / 自動移行）
     ↓ 自宅離脱が安定動作
Phase 2         動的アンカー（層B / カフェ・職場の置き忘れ）
     ↓ 台帳が定着してから
Phase 3         状態機械（current_step / 着手支援 / 中断復帰）
                ※ここで初めてLLM APIが必要になる
     ↓ 閾値の妥当な範囲が見えてから
Phase 4         BOOTH販売
```

出発時刻推定はMVP内で自動的に段階移行するため、独立したフェーズを持たない。

### Phase 3 に向けたメモ

移動時間は**着手支援の枠としては最良**である。電車の20分は他に何もできない時間で、本人もそれを認識している。「今この20分でやる1手」を出すには理想的な条件。

ただし忘れ物リマインドとは要求が正反対になる。忘れ物は「短く、単語だけ、引き返せる間に」。着手支援は「腰を据えて、選択肢を出して」。**同じ移動中でも扱いが逆**なので、Phase 3 設計時に混同しないこと。

### 販売時の論点（Phase 4）

- **設定の摩擦**: GASデプロイ、URL取得、トークン設定で脱落者が出る。手順を最小化する
- **配布形態**: Wrapper.gs パターンでコアロジックを保護
- **二段階価格**: 基本版=時刻トリガーのみ / 上位版=位置情報連携（ミキと同構成）
- **プラットフォーム**: iOSショートカットは iCloud リンクで雛形配布可。Android は配布手段が弱く、当初はiOS限定+手順書のみとする割り切りも検討
- **表現の注意**: 治療・改善効果を謳わない。「行動補助」「実行支援ツール」の範囲に留め、薬機法まわりの問題を回避する
- **API規約**: Open-Meteo の商用利用条件、LINE の通数上限を再確認
- **初期値**: 自分で2〜3週間回して妥当な閾値範囲が見えてから同梱する
